### What the statuses mean

- **triggerable**: an existing openbench task fires the path with the current runner. Either the task runs unchanged, or it is a copy of an existing workspace and checker with a sentence added to the start of `instruction.md`. Those copies have proposed `trig-*` names; none of them exist in the repo yet.
- **needs fixture**: needs new workspace files, a runner, proxy or config change, or a toolchain the box does not have.
- **untriggerable**: cannot fire with Opus 5.5 on Vertex as configured. Only #18140, and the reason is model routing, not headless mode: any model id containing `claude` gets `anthropic.txt`. No PR is untriggerable *because* `opencode run` is headless. #623's prompt sentence is always sent, but the behaviour it asks for needs a second user turn, which headless runs never have.
- **incompatible**: the five known rows (#913, #984 and #1248 need the beta SDK; #3369 and #3418 need the v0.15 stream). PR #9 (`fbb8ef2`) targets the shared root cause: it writes `CACHE_VERSION`, sets `OPENCODE_DISABLE_DEFAULT_PLUGINS=1`, and marks SDK drift as infra. But its notes do not claim these builds now run against real Opus streams; that was verified on stubs only. So they stay incompatible until the Developer's per-era smoke tests (913/1248/3418 eras) pass. Their trigger tasks are still specified so they can run right after.

## Read this before using `trigger-evidence.csv`

No `results/ab/<pr>/transcripts/` directory exists yet; every saved cell predates `fbb8ef2`. I built the patterns from the code that writes each format, checked them against the real stub artifacts in `/tmp/repro`, and tested them with Python `re` and GNU `grep -E` on synthetic samples in each format. Every merge-build sample matched and every parent-build sample did not (59/59 checks; `scratch/test_trigger_regex.py`). What each cell will contain under `fbb8ef2`:

- `transcripts/<side>/<run_id>.txt` holds a 3-line header, then stdout, then stderr. Every build here accepts `--print-logs` (checked with `run --help`), so the OpenCode log lines go to **stderr inside this file** (`INFO  <ts> +Nms service=… key=val … <message>`), and the `log/` copy will be empty.
- Builds from #3052 on run with `--format json`, so stdout is one compact JSON event per line: `{"type":"tool_use",…,"part":{…,"tool":"read","state":{"status":"completed","input":{…},"output":"…"}}}`. Newlines inside output appear as the two characters `\n`, which the patterns account for. **#3052–#13331 emit only completed tool calls**; tool *errors* (#3052, #3418, #13198) appear only in storage. #17053 and later also emit errors.
- Builds #623–#2334 have no `--format json`. Their stdout is the coloured text UI (`| Bash     cmd`), and tool outputs are not printed.

### Gaps in fbb8ef2's evidence capture (`_preserve_opencode_evidence` copies only `$XDG_DATA_HOME/opencode/{storage,log}`)

- **G1, the biggest:** builds #623, #913, #984, #1248 and #2334 keep sessions under `$XDG_DATA_HOME/opencode/project/<projectID>/storage/`, not `opencode/storage/`. I confirmed this in `storage/storage.ts` (`path.join(app.path.data, "storage")`) and in the `/tmp/repro/913T` and `2334NM` layouts. The copier misses it, and these builds print no tool outputs, so **#913, #984, #1248 and #2334 tool-level evidence would be lost**. Fix: also copy `opencode/project/*/storage`.
- **G2:** #17053 and later store sessions in `opencode.db` (SQLite), which is not copied. Stdout JSON still carries main-session tool calls in full (completed and errors), so the patterns work. Subagent-internal tool calls are not in stdout; only the task tool's own output is.
- **G3:** #2367–#13331 use `opencode/storage/` (pretty-printed JSON, `"key": "value"` with a space). That is copied, and the patterns allow the optional space.
- Run `grep -E -r` over each cell's `.txt` and its evidence directory. All patterns work line-by-line. #13198's uses a backreference (`\1`), which GNU `grep -E` and Python `re` both support.
