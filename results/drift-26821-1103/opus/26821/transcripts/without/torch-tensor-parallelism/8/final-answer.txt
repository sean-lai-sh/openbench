I wrote `parallel_linear.py` with both classes. I ran a test with 1, 2 and 4 processes using PyTorch's CPU (`gloo`) backend, comparing each class against a plain `nn.Linear`. For both classes, the outputs, the weight and bias gradients on each rank's share, and the input gradients all matched the reference.

`master_weight` is expected in the usual `nn.Linear` layout, `(out_features, in_features)`.

**`ColumnParallelLinear`**
- Each rank keeps an equal slice of the output features (rows `rank*out/ws : (rank+1)*out/ws` of the weight).
- The bias is split the same way and starts at zero.
- The forward pass computes this rank's part of the output, then joins all ranks' parts along the last dimension (the `all_gather` step).
- Going backward, each rank takes its own slice of the incoming gradient. Gradients for the input are summed across ranks (the `all_reduce` step), so the input gradient is correct.

**`RowParallelLinear`**
- Each rank keeps an equal slice of the input features (weight columns `rank*in/ws : (rank+1)*in/ws`).
- The bias is full size on every rank, starts at zero, and is added once after the partial outputs are summed with `all_reduce`.
- The forward pass accepts either the full input, which it splits itself, or an input that has already been split per rank. It tells them apart by the size of the last dimension.

**Things to know:**
- Both feature sizes must divide evenly by the number of ranks; otherwise the constructor fails an assertion.
- If no process group has been set up, the classes act as a single process (one rank, rank 0) instead of raising an error.
