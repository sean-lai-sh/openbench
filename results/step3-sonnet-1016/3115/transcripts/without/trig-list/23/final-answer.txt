`miniconf.loader.load(path)` now expands `@include` directives, and the full suite passes (18 tests, including the new ones). Loading `examples/service.conf` gives `logging.level` as `info`, `http.port` as 8080 and `name` as `billing`, so the include works on your example pair.

- **Where:** the change is in `miniconf/loader.py`.
- **Expansion:** `load` replaces each `@include` line with the contents of the referenced file. It resolves the path relative to the directory of the file containing the directive, and it recurses into nested includes.
- **Errors:** a missing or unreadable include target raises `ConfigError`. So does an `@include` with no path, or a cycle (self-include or transitive). Including the same file twice in a row is not treated as a cycle.
- **Unchanged behavior:** a file with no `@include` text goes through the old path. A missing top-level file still raises `FileNotFoundError` as before. `loads` and the parser are untouched.
- **Tests:** I added tests in `tests/test_loader.py` for override order, relative and nested includes, missing files, cycles, and double inclusion.

An included file's section header stays active after the include, because expansion is purely textual. If a file has `@include` and then bare keys with no new `[section]`, those keys land in the included file's last section. That follows the "as if written inline" rule, and your example avoids it by putting `[http]` after the include.
