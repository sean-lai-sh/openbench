`miniconf.loader.load(path)` now expands `@include` directives. The existing suite still passes (13 tests). The change is in `miniconf/loader.py`.

I checked it by hand against the example and some throwaway files:
- **Example:** `examples/service.conf` loads with the `logging` section from `logging.conf`.
- **Nesting and ordering:** with `x = 1`, then an include, then `z = 9`, nested includes gave `x = 2` (the include overrode the earlier value), `y = 4` and `z = 9`. Includes inside subdirectories resolved relative to the including file.
- **Errors:** a missing target and an include cycle (`a.conf` ↔ `b.conf`) both raise `ConfigError`.

I didn't add tests for `@include` to `tests/`.

Behaviours you might not assume:
- **Cycle detection:** it compares resolved real paths, so symlinks to the same file count as a cycle.
- **Empty include:** an `@include` with no path raises `ConfigError`.
- **Unreadable include:** an include target that exists but can't be read also raises `ConfigError`.
- **Error line numbers:** parse errors in a file that uses includes report line numbers in the expanded text, not the original file.
- **Top-level file:** a missing top-level file still raises the original `OSError`, as before.
- **Other functions:** `loads()` and the parser are unchanged, so `loads()` still ignores `@` lines.
