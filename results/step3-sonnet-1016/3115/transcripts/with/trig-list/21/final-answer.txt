`miniconf.loader.load(path)` now expands `@include` directives, and the existing 13 tests still pass. I also ran it by hand on throwaway files and on `examples/service.conf`, which loaded as expected. I haven't added tests for `@include` to `tests/`.

- **Inline expansion:** an `@include` line is replaced by the included file's lines, then parsed as usual. I added no new test files and removed my scratch files.
- **Relative paths:** each include resolves against the directory of the file containing the directive.
- **Ordering:** a key set after the directive overrides the included value. In my check, `a=3` after the include beat `a=2` from the included file.
- **Nesting:** includes expand recursively. In my check, `m.conf` included `sub/b.conf`, which included `../c.conf`.
- **Missing file:** raises `ConfigError`.
- **Cycles:** a file that includes itself, directly or through other files, raises `ConfigError`.

Two behaviours go beyond the spec:
- **Path argument:** `@include` with no path, or with an unreadable or non-UTF-8 target, also raises `ConfigError`. Paths containing spaces work.
- **Section carry-over:** because expansion is purely positional, a key placed after `@include logging.conf` lands in `[logging]`, which is the last section the included file opened. This follows from the spec, but you may not expect it.

A missing top-level file still raises the raw `FileNotFoundError`, as before. `loads()` and the parser are unchanged. The change is in `miniconf/loader.py`.
