`miniconf.loader.load(path)` now expands `@include` directives. The change is in `miniconf/loader.py`. The existing 13 tests pass under `unittest`, because `pytest` isn't installed here. I didn't add tests for includes.

Beyond the test suite, I ran three checks by hand:
- **Example files:** `examples/service.conf` loads with the logging section pulled in.
- **Cycle:** two files that include each other raise `ConfigError`.
- **Missing file:** an include of a nonexistent path raises `ConfigError`.

How it behaves:
- **Paths:** each include is resolved relative to the directory of the file containing it.
- **Nesting:** nested includes are expanded recursively.
- **Cycles:** a file that includes itself directly or through other files raises `ConfigError`. The same file included twice in separate places is not a cycle and is allowed.
- **Unreadable targets:** a missing file, a directory, or any other read failure raises `ConfigError`.
- **No path:** an `@include` with no path also raises `ConfigError`.

Two things you might not assume:
- **Sections leak:** because expansion is purely textual, a section header inside an included file stays active for the lines after the `@include`. This follows from "as if written where the directive appears". In the example, `service.conf` re-declares `[http]` right after the include, so it isn't affected.
- **Line numbers:** parse errors report line numbers in the expanded text, not in the original file.

`loads()` and `parse_lines` are unchanged, so `@include` lines passed to `loads()` are still ignored.
