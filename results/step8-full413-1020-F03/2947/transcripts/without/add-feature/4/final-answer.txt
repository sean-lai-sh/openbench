`miniconf.loader.load(path)` now expands `@include` directives. The change is in `miniconf/loader.py`.

- **Expansion:** An `@include` line is replaced with the included file's lines before parsing. Paths resolve relative to the including file's directory, and nested includes expand recursively. Because the expansion is positional, later assignments win.
- **Errors:** A missing or unreadable include target raises `ConfigError`. So does an `@include` with no path, and so does a cycle, whether direct or transitive. Cycles are detected by comparing resolved paths (`realpath`), so symlinks count.
- **Unchanged behavior:** `loads()` and `parse_lines` are untouched. A missing top-level file still raises `FileNotFoundError`, as it did before.

The existing 13 tests pass. `examples/service.conf` loads correctly: `[logging] level` is `info`, `[http] port` is `8080`, and `name` is `billing`. A temporary a↔b include cycle and a missing-include file both raised `ConfigError`. I didn't add new test cases to `tests/`.

An included file's `[section]` header stays active after the include ends, because the expansion is literal. In `service.conf`, the `[logging]` header from `logging.conf` is in effect until `[http]` appears. A key placed right after an `@include` line therefore lands in the included file's last section. Say so if you'd rather the section reset after an include.

Line numbers in parser error messages now refer to the expanded text, not the original file, when includes are present.
