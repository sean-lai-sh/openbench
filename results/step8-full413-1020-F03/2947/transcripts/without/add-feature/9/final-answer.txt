`miniconf.loader.load(path)` now expands `@include` directives as the task describes, and the 13 existing tests still pass. I made the change in `miniconf/loader.py`.

I ran `examples/service.conf` and it loads with the `logging` section pulled in. I also ran throwaway files, since deleted, for override order, a nested include through a subdirectory, a missing target and a cycle. A key assigned after an include overrides the included value. A cycle or a missing target raises `ConfigError`.

I didn't add tests for `@include` to the `tests/` suite.

A few behaviours you might not assume:
- **Section carry-over:** because expansion is purely textual, a `[section]` header inside an included file stays active for the lines after the include, in the including file. That matches "as if written there", but a following include or key can land in an unexpected section.
- **Repeated includes:** including the same file twice, without a cycle, is allowed.
- **Directive form:** the path is everything after `@include`, so paths with spaces work. An `@include` with no path raises `ConfigError`.
- **Unreadable files:** an include target that exists but can't be read or decoded also raises `ConfigError`.
- **Line numbers:** parse errors report line numbers in the expanded text, not in the original file.

`loads()` and the parser are unchanged, so `loads()` still ignores `@` lines and does not expand includes.
