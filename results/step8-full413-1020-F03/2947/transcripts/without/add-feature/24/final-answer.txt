`miniconf.loader.load(path)` now expands `@include` directives, and the full suite passes (17 tests, including 4 new ones for includes). I also ran it on `examples/service.conf`. It reads `level = info` from the included `logging.conf`, and `name` and `port` still come through.

The change is in `miniconf/loader.py`, and the new tests are in `tests/test_loader.py`.

- **Expansion:** The loader replaces each `@include` line with the included file's text before parsing. Nested includes expand recursively.
- **Relative paths:** Each include path is resolved against the directory of the file containing the directive, not the working directory.
- **Missing or unreadable target:** An include that can't be read raises `ConfigError`. That covers a missing file, a directory, a permissions problem and a decoding error. A missing top-level file still raises `FileNotFoundError`, as before.
- **Cycles:** An include chain that revisits a file raises `ConfigError`. That covers a file including itself and longer loops, and symlinks are resolved first. The same file included twice by different parents (not a cycle) is allowed.
- **No path:** A bare `@include` with no path raises `ConfigError`. I added that case; the spec didn't cover it.
- **Unchanged paths:** `loads()` and `parse_lines` are untouched, so a string passed to `loads()` still ignores `@include`.

Because expansion is purely textual, a `[section]` header inside an included file stays active for the lines after the `@include`. This follows from "as if written there". Line numbers in parse errors also refer to the expanded text, not the original file.
