`miniconf.loader.load(path)` now expands `@include` directives, and the existing 13 tests still pass. The change is in `miniconf/loader.py`.

I also ran `examples/service.conf` and two throwaway files that I deleted afterwards:
- **Example:** `service.conf` loads with `logging.level` = `info` and `http.port` = `8080`.
- **Missing target:** an include of a file that doesn't exist raises `ConfigError`.
- **Cycle:** `a.conf` including `b.conf`, which includes `a.conf`, raises `ConfigError`.

- **Expansion:** an `@include` line (first token `@include`, then a path) is replaced inline by the included file's lines, recursively, before parsing. `loads()` and the parser are untouched.
- **Paths:** each include is resolved relative to the directory of the file containing the directive.
- **Cycles:** I track the chain of files currently being expanded. A file included twice without a cycle is allowed.
- **Errors:** an `@include` with no path also raises `ConfigError`. A missing top-level file still raises `FileNotFoundError` as before.

Because expansion is purely textual, a `[section]` header inside an included file stays active for the lines after the `@include`. For example, keys placed after `@include logging.conf` land in `[logging]`. That matches the "as if written inline" requirement.

Line numbers in parse errors now refer to the expanded text, not the original file, whenever includes are used.
