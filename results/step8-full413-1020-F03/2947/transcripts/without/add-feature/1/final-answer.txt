`miniconf.loader.load(path)` now expands `@include` directives as specified. The change is in `miniconf/loader.py`.

- **Checks run:** The existing suite passes (13 tests, run with `unittest` because pytest isn't installed). I also ran `examples/service.conf` and some throwaway files by hand: ordering, nesting with a relative path, a missing target, and two cycles. I didn't add tests for `@include` to `tests/`.
- **Expansion:** Each `@include <path>` line is replaced by the included file's lines, then the normal parser runs over the result. A key set after an include overrides the included value, and a key set before it is overridden. In my nested test, `x=1` before an include that set `x=5` ended up as 5, and a later `y=2` beat the included `y=9`.
- **Paths:** An include path is resolved relative to the directory of the file that contains it. Nested includes are expanded recursively.
- **Errors:** A missing or unreadable include target raises `ConfigError`, and so does an `@include` line with no path. A file that includes itself, directly or through other files, raises `ConfigError` instead of looping. A file included twice without a cycle is allowed.
- **Unchanged:** `loads` and the parser are untouched. If the top-level file itself is missing, you still get the same `FileNotFoundError` as before.

One behaviour follows from literal inline expansion. If an included file ends inside a `[section]`, keys that come after the `@include` line fall into that section. `examples/service.conf` avoids this because `[http]` follows its include. Line numbers in parse errors also count the expanded text, so they can differ from the original file's line numbers when includes are present.
