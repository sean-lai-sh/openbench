`miniconf.loader.load(path)` now expands `@include` directives. The 13 existing tests still pass, and I tried each required behaviour by hand with a script, but I didn't add any new tests to `tests/`.

**What changed** (all in `miniconf/loader.py`): a new helper `_expand(path, stack)` reads the file and goes through it line by line. When the first word of a line is exactly `@include`, it puts the target file's lines (themselves expanded) in place of that line. The expanded lines then go to the existing `parse_lines`. `loads()` and the parser are unchanged.

**What I checked:**
- **Example:** `examples/service.conf` loads with the top-level keys, the `[logging]` section from `logging.conf`, and `[http]`.
- **Relative paths:** an include is found relative to the folder of the file that contains it, including through nested folders (`a.conf` → `sub/b.conf` → `c.conf` in `sub/`).
- **Override:** a key set after an include replaces the included value; a key set before it is replaced by the include.
- **Missing file:** an include that points to a file that doesn't exist raises `ConfigError`.
- **Cycles:** a file that includes itself, directly or through another file, raises `ConfigError`. Including the same file twice without a loop is still allowed.

**Things you might not expect:**
- If the file passed to `load()` doesn't exist, it still raises `FileNotFoundError` as before. Only a missing include target raises `ConfigError`, so existing behaviour stays the same.
- A bare `@include` with no path raises `ConfigError`. The spec didn't cover this case.
- Because expansion is purely positional, any `[section]` opened in an included file stays open afterwards. In the example, if `service.conf` set keys after the include and before `[http]`, they would land in `[logging]`, not at the top level.
