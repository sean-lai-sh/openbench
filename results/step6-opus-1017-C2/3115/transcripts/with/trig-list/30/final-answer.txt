`miniconf.loader.load(path)` now handles `@include` directives. All the required behaviours work: inline expansion, nesting, missing files and cycles. The existing 13 tests still pass, and I didn't add any new ones.

I tried it against `examples/service.conf`, which loads the `[logging]` values from `logging.conf`. I also built some throwaway files in a temp folder to check the rest:
- **Relative paths and nesting:** an include in a subfolder that pulls in another file resolves relative to the subfolder, not the working directory.
- **Ordering:** for a key set before, inside, and after an include, the last assignment wins.
- **Cycles:** a file that includes itself through two other files raises `ConfigError` with the include chain in the message.
- **Missing file:** an include pointing at a file that doesn't exist raises `ConfigError`.

The change is all in `miniconf/loader.py`. Before parsing, it replaces each `@include` line with the contents of the target file, then hands the result to the existing `parse_lines` unchanged. `loads()` (parsing from a string) still ignores `@include`, since only `load()` was in scope.

Three behaviours you might not assume:
- **Sections carry across:** because the included lines are dropped in as if written there, a `[section]` opened in an included file stays active for the lines after the `@include` in the parent file.
- **Bare `@include`:** an `@include` line with no path also raises `ConfigError`.
- **Missing top-level file:** if the file passed to `load()` itself doesn't exist, it raises the same `OSError` as before, not `ConfigError`.
