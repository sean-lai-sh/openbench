`miniconf.loader.load(path)` now handles `@include` directives, and the existing 13 tests still pass. The change is all in `miniconf/loader.py`.

**How it works:** each `@include` line is replaced by the lines of the target file, and nested includes are expanded the same way. The expanded text is then passed to the existing `parse_lines`, so "later assignment wins" gives the override behaviour you described. The include path is taken relative to the directory of the file that contains the directive.

**Errors:**
- A missing include target raises `ConfigError`.
- A cycle raises `ConfigError` and shows the chain of files in the message. Files are compared by their resolved real path, so a cycle is still caught when it goes through a symlink or a different relative path.
- Including the same file twice from different places is allowed, because only an include back up the current chain counts as a cycle.

**What I tested:**
- `examples/service.conf` loads with values from both files (`billing`, `info`, `True`, `8080`).
- In throwaway temp files, I checked override order in both directions, nested includes in a subdirectory, a transitive cycle and a missing include.

**Things you might not expect:**
- If the top-level file passed to `load()` doesn't exist, it still raises `FileNotFoundError` as before, not `ConfigError`. Only missing *include* targets raise `ConfigError`.
- An `@include` line with no path raises `ConfigError`.
- Everything after `@include` is treated as the path, so paths with spaces work, and `~` is expanded to the home directory.
- A `[section]` header inside an included file stays active after the include ends, since the lines are simply inserted in place. In the example this doesn't matter because `service.conf` starts `[http]` straight after the include.
