`miniconf.loader.load(path)` now expands `@include` directives. The existing 13 tests still pass, and I checked each of the required behaviours with throwaway files (since deleted). I didn't add permanent tests to `tests/`.

The change is all in `miniconf/loader.py`; `loads()` and the parser are untouched. Before parsing, `load()` replaces every line whose first token is `@include` with the lines of the named file.

Results of the checks:
- **Example:** `examples/service.conf` loads with `name=billing`, `logging.level=info`, `logging.json=True` and `http.port=8080`.
- **Nesting and override:** a three-level include using a `sub/` folder worked. A key set after an include replaced the included value, and a key set before an include was replaced by it.
- **Relative paths:** each include path is resolved from the folder of the file that contains it, not the working directory.
- **Missing target:** raises `ConfigError`.
- **Cycles:** a file including itself, and two files including each other, both raise `ConfigError`.

Three behaviours you might not assume:
- **Section carry-over:** expansion is purely line-by-line, so if an included file ends inside a `[section]`, keys after the `@include` land in that section. In `service.conf` this doesn't matter because `[http]` comes straight after.
- **Repeated includes are allowed:** cycle detection only tracks the chain of files currently being expanded. Two files can both include the same third file without an error.
- **Errors:** an `@include` with no path raises `ConfigError`. A missing top-level file passed to `load()` still raises `FileNotFoundError`, as it did before.
