`load(path)` now handles `@include`; the change is all in `miniconf/loader.py`. The existing 13 tests still pass. I checked the new behaviour with a quick script but didn't add tests for it to the suite.

**What the script showed:**
- **Example files:** `examples/service.conf` loads with the included logging settings (`level = info`, `json = True`) plus its own `name` and `[http]` values.
- **Ordering:** a key set before an include is overridden by it, and a key set after an include overrides it.
- **Nesting and relative paths:** a nested include (`a.conf` → `sub/b.conf` → `sub/c.conf`) worked, with each path resolved from the including file's directory.
- **Cycles:** a file that eventually includes itself raises `ConfigError`, and the message lists the chain of files.
- **Missing file:** an include that points to a file that doesn't exist raises `ConfigError`.

**How it works:**
- `load` expands each `@include` line into the included file's lines before handing the text to the parser.
- A cycle is detected by tracking only the chain of files currently being opened. So one file can still be included in two separate places, as long as it never includes itself.
- An `@include` with no path also raises `ConfigError`.

**Things you might not expect:**
- Because expansion is purely inline, if an included file opens a `[section]`, any keys after the `@include` line land in that section until the next header. This matches the spec, and the example is fine because `[http]` comes right after the include.
- Paths containing spaces work, but quotes around a path aren't removed.
- If the top-level file passed to `load` is missing, it still raises `FileNotFoundError` as before, not `ConfigError`.
- `loads(text)` doesn't expand includes; only `load(path)` does, as specified.
