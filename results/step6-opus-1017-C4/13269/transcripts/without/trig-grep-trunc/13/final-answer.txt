All 25 tests pass now. `python3 -m unittest` started with 18 failures and now reports `OK`.

I ran the `self` grep first as you asked. It returned 100 matches and was cut off, so I used the test run and the source files to find the bugs instead. There were seven, each one line, in seven files:

1. **`taskflow/queue.py:40`** – The sort key was `(seq, -priority)`, so tasks came out in arrival order and priority only broke ties. Changed to `(-priority, seq)` so higher priority goes first, as the comment says.
2. **`taskflow/retry.py:100`** – `should_retry` checked `attempts_made < max_attempts - 1`, which stopped one attempt early. Changed to `< max_attempts`.
3. **`taskflow/config.py:77`** – `deep_merge` swapped its arguments when merging nested settings, so the defaults overwrote a task's own `retry` settings. This is why the retry pipeline tests failed even though they look like retry problems.
4. **`taskflow/statemachine.py:76`** – The check that each task started in one scheduling round has equal or lower priority than the one before it was backwards (`>=`). Once the queue order was fixed, this check rejected the correct order and marked tasks as failed. Changed to `<=`.
5. **`taskflow/resources.py:99`** – Releasing resources always gave back 1 unit instead of the task's full cost. Tasks that needed 2 units could then never start.
6. **`taskflow/events.py:34`** – The prefix match was reversed (`prefix.startswith(topic + ".")`). As a result, the run history never received any `job.term.*` events (succeeded, failed or skipped), so its outcome counts were always zero.
7. **`taskflow/scheduler.py:264`** – When a task failed for good, only its direct dependents were marked skipped. It now uses `dag.transitive_dependents` (already in `dag.py`) so everything downstream is skipped.

I didn't change any tests.
