I fixed eight logic bugs across seven files in `taskflow/`, and `python3 -m unittest` now passes all 25 tests. I didn't change any tests.

As you asked, I started with a grep for `self`. It matched 1,325 lines, too many to narrow anything down, so I went by the test failures instead.

**First round** (these three accounted for the unit-test failures and most of the retry pipeline failures):
1. **`retry.py:100`**: `should_retry` allowed one attempt fewer than its budget (`< max_attempts - 1`). Changed it to `< max_attempts`, which matches the docstring.
2. **`queue.py:40`**: the queue sorted on `(seq, -priority)`, so tasks came out in insertion order instead of by priority. Changed it to `(-priority, seq)`.
3. **`config.py:77`**: the nested merge had its arguments swapped, so the defaults overwrote each task's own settings. For example, a task's `retry.max_attempts: 3` was replaced by the default of 1.

**Second round** (these only showed up once the first three were fixed):
4. **`events.py:34`**: the prefix match was reversed (`prefix.startswith(topic + ".")`). As a result, subscribers to `job.term` never received events like `job.term.failed`, and the run history came out empty.
5. **`resources.py:99`**: releasing resources subtracted 1 instead of the task's full cost. The pool stayed partly occupied, so later tasks could never start.
6. **`statemachine.py:76`**: the check on dispatch order within a tick was inverted (`>=` instead of `<=`). Once the queue was fixed, it rejected the correct highest-priority-first order and marked those tasks as failed.
7. **`scheduler.py:264`**: when a task failed for good, only its direct children were skipped; tasks further down stayed `PENDING`. It now uses the graph's existing `transitive_dependents`, as its docstring describes.

Number 6 is an example of the masking you mentioned: the bad queue ordering hid the bad check, and fixing one made the other visible.
