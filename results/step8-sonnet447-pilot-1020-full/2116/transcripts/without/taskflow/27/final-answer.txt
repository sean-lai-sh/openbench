`python3 -m unittest` now passes all 25 tests. I didn't touch the tests, and I didn't read or change the modules the failing tests don't exercise (planner, stats, metrics and the rest), so any bugs there are unchecked.

There were six root causes. Several of the 18 failures shared one:

1. **`queue.py`**: `_Entry.sort_key` returned `(seq, -priority)`, so the queue ordered by insertion first and ignored priority. It now returns `(-priority, seq)`.
2. **`retry.py`**: `should_retry` used `attempts_made < max_attempts - 1`, which gave one attempt too few. It now uses `attempts_made < max_attempts`. This fixed the retry tests.
3. **`statemachine.py`**: `batch_order_ok` required priority to be non-decreasing within an admission batch, but the docstring says non-increasing. It now checks `current <= prev`.
4. **`resources.py`**: `ResourcePool.release` did `used -= 1` instead of `used -= cost`, so resources leaked and later tasks never got admitted. Fixing it cleared the resource tests.
5. **`scheduler.py`**: `_cascade_skip` used `dag.dependents`, which returns only direct children. It now uses `transitive_dependents`, so a permanent failure skips everything downstream.
6. **Two more, in `config.py` and `events.py`**:
   - `config.py`: `deep_merge` recursed with its arguments swapped, so the defaults overrode the task's own values. This is why `retry.max_attempts` came out as 1 instead of 3 or 5.
   - `events.py`: `_prefix_matches` had the `startswith` check backwards, so `job.term` subscribers never received `job.term.failed` and similar events. The history tests were failing because of this.
